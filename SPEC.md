# Claptrapedia workshop specification

Build Claptrapedia Workshop, a local app for maintaining the [Claptrapedia](https://claptrapedia.com) Borderlands catalogue. It turns game extracts and reference material into reviewed catalogue changes, then exports a PostgreSQL migration for the public site.

The first release covers Borderlands 1. Implement weapon families and the enemies, locations and loot sources needed to describe their acquisition. Add other record types and games only when their data and site models exist.

## Repositories and ownership

| Repository | Owns |
| --- | --- |
| [`claptrapedia/extractions`](https://github.com/claptrapedia/extractions) | Raw game extractions used as workshop inputs |
| [`claptrapedia/workshop`](https://github.com/claptrapedia/workshop) | Import, research, review, local drafts, SQL generation and testing |
| [`claptrapedia/database`](https://github.com/claptrapedia/database) | PostgreSQL DDL, catalogue migrations, generated schema snapshot and database deployment |
| [`claptrapedia/site`](https://github.com/claptrapedia/site) | Public website, SQL queries via Postgres.js (`postgres`) and website deployment |

Treat the database repo’s `db/migrations/` as the source of truth for schema and catalogue changes. Its generated `db/schema.sql` is the current schema, including the `COMMENT` text on tables and columns. Read those comments before generating SQL. Take table names, column names, data types, constraints and conflict keys from that snapshot and from the migrated local database. If the schema cannot represent a catalogue fact, stop and report that fact for review. Do not invent a table inside a data migration. A structural change belongs in a `_STRUC_` file. This workshop does not write those files.

### Database contract

Target PostgreSQL 17.2. Catalogue objects live in the `catalogue` schema. `public` holds dbmate’s `schema_migrations` table and the `pg_trgm` extension. Qualify every catalogue table, for example `catalogue.enemies`. The database does not set `search_path`. `pg_trgm` stays in `public` so `similarity` and the `%` operator resolve on the default path.

The migrated tables are `games`, `releases`, `dlcs`, `playthroughs`, `rarities`, `game_rarities`, `elements`, `game_elements`, `effects`, `manufacturers`, `game_manufacturers`, `classes`, `skill_kinds`, `families`, `ranks`, `rank_playthroughs`, `characters`, `skill_trees`, `action_skills`, `skills`, `enemies`, `locations`, `missions`, `mission_enemies`, `card_stats`, `game_card_stats`, `item_types`, `item_subtypes`, `items`, `item_manufacturers`, `item_rarities`, `item_elements`, `item_skills`, `item_flavours`, `item_abilities`, `aliases`, `prefixes`, `item_references`, `item_tags`, `keywords`, `pools` and `drops`. Weapon, shield and grenade extension tables do not exist. `items` has `id`, `game_id`, `dlc_id`, `slug`, `name`, `item_type_id`, `subtype_id`, `character_id`, `plain`, `projectile_min`, `projectile_max`, `summary` and `description`. `slug` and `name` are unique within the game. `projectile_min` and `projectile_max` are the xN beside damage on a weapon. Both are null when the card shows no xN, and on every item that is not a weapon. A fixed x6 stores 6 and 6. Damage, accuracy, fire rate and magazine are not columns. Do not invent one, and do not invent a drop chance column. Do not emit SQL for a table or column that is absent from `db/schema.sql`.

`id` is a stable lowercase kebab-case key the workshop chooses, such as `bone-head`. It is not a generated number or UUID. The published Borderlands 1 game id is `borderlands`. `slug` is the public URL and may change. Names and slugs are editable. Use the primary key as the conflict target. That is `(id)` on `games`, `rarities`, `elements`, `effects`, `manufacturers`, `classes`, `skill_kinds`, `families`, `ranks`, `item_types` and `card_stats`, and `keyword` on `keywords`, and `(id, game_id)` on `releases`, `dlcs`, `playthroughs`, `characters`, `enemies`, `locations`, `missions`, `items` and `pools`. `skill_trees` is `(id, character_id, game_id)`. `rank_playthroughs` is `(rank_id, game_id)`. Link tables use the whole primary key: `(game_id, rarity_id)` on `game_rarities`, and the same shape for `game_elements`, `game_manufacturers` and `game_card_stats`. `mission_enemies` is `(mission_id, game_id, enemy_id)`. `item_manufacturers` is `(item_id, game_id, manufacturer_id)`. `item_rarities` is `(item_id, game_id, rarity_id)`. `item_elements` is `(item_id, game_id, element_id)`. `item_skills` is `(item_id, game_id, skill_id)`. `item_flavours` and `item_abilities` are `(item_id, game_id, position)`. `aliases` and `prefixes` are `(item_id, game_id, name)`. `item_references` is `(item_id, game_id, url)`. `item_tags` is `(item_id, game_id, keyword)`. `skills` and `action_skills` are `(id, character_id, game_id)`. `item_subtypes` is `(id, item_type_id)`. `drops` has no `id`. Its conflict target is `(item_id, game_id, enemy_id, location_id, mission_id, pool_id)`, and nulls compare equal. A DLC reference is the pair `(dlc_id, game_id)`. Null `dlc_id` means the base game.

Rarities, elements, manufacturers, classes, skill kinds, families, ranks, item types, item subtypes and card stats are shared across games. A `game_*` row says that value exists in that game. Pools are per game. A world pool is a `drops` row with `pool_id` set and the enemy, location and mission null. A dedicated source is a separate `drops` row. Do not add an item-pools table. An alias is an earlier item name, not a second item. A prefix belongs to one item. The same word on another item is another row. Read the `COMMENT` text for the rest of these rules.

Keep `games`, `releases` and `dlcs` distinct. Borderlands 1 is a game. The original edition, GOTY and GOTY Enhanced are releases of that game. A BL1 Enhanced capture supports claims about that release. A DLC is the pack that introduced an enemy, not the place where it appears. `family_id` points at the shared species, such as `skag`. `rank_id` points at the shared tier, such as `badass`, and is null when the enemy is not a tier. `position` is display order. `kind` on an enemy is `named`, `boss` or `mob`. A named enemy is not always a boss. A character is the playable person in one game, such as Lilith. `class_id` points at the shared class, such as `siren`. Another game's Siren is another character row with the same `class_id`. A class, a skill kind, a family, a rank, an item type or an item subtype is in a game when a row there uses it. Do not add a `game_classes`, `game_skill_kinds`, `game_families`, `game_ranks`, `game_item_types` or `game_item_subtypes` table. A rank has no `game_id`. The same word, such as Badass, is one row in every game, and its summary must not name a playthrough. Which run uses that name is `rank_playthroughs`. A rank such as Whelp has no playthrough row. A character is not an enemy. A skill belongs to one character, such as Roland's Impact. `id` is the skill within that character, such as `impact`. `tree_id` points at that character's branch, such as `infantry`, and it is required. `kind_id` points at the shared skill kind, such as `passive` or `kill`. An action skill is a row in `action_skills`, not in `skills`. `cooldown` and `duration` are the base seconds before other skills change them. `duration` is null when the skill is not a timed mode. The site prints `name` from the kind, the tree, the family, the rank, the item type and the item subtype. That name is the exact label. A different wording of the same thing is not a new row. `tier` 0 is the first row. `points` is the maximum. The same skill name on another character is another row. Do not hang a skill on the class. An item type is the inventory bucket, such as `weapon` or `grenade-mod`. An item subtype is the second label inside that bucket, such as `shotgun` or `mirv`, and its primary key includes `item_type_id`. Class mods and artifacts have no subtype. A character is not a subtype. `items.item_type_id` is required. `items.subtype_id` is required for a weapon, a shield and a grenade mod, and null for a class mod or an artifact. The foreign key is `(subtype_id, item_type_id)`. `items.character_id` is required for a class mod or an artifact and null for the other buckets. It is the person, such as `roland`, not the shared class. `items.plain` is true when a spawn can have no element, including a gun that never has one. `item_elements` lists every element a spawn can have. Do not insert a `none` element. `multiplier_min` and `multiplier_max` on that row are the x1 to x4 tech rating for that element. A fixed x4 stores 4 and 4. A roll from x1 to x3 stores 1 and 3. Leave both null when that element has no tech rating, such as a shield. `projectile_min` and `projectile_max` are how many projectiles one shot fires. They are not the tech rating and not the ammunition used per shot. `item_manufacturers` is one brand on a gun, shield or grenade, and each brand printed on a class mod. A part's brand is not a row there. `item_rarities` is every tier the item can spawn as. A unique is one row. Those three joins must use a rarity, element or manufacturer already linked to that game. `item_skills` is the bonus points a class mod adds to one of that character's tree skills. `points` may sit above the skill's own maximum. It is not an action skill, and a card line that is not a skill point stays on `item_abilities`. `item_flavours` is a flavour line and what that line does. `kind` is `red` or `white`. `quote` is the words on the card. `summary` is the one-line effect. `description` is the longer effect. `notes` is an aside that is not the effect. `self` is true when the effect applies to the wielder. An item has at most one red row. A white row is other flavour text, such as a joke on the card. Do not store a flavour quote on `item_abilities`.

Generated values must satisfy the domains in `db/schema.sql`. `catalogue.slug` is lowercase kebab-case. `catalogue.summary` is one line. `catalogue.non_empty` rejects blank text. `catalogue.url` is an absolute http or https address with no spaces. Leave an unknown optional value null. Do not write an empty string.

`description` is the long body and may run to more than one paragraph. Use it for lore on manufacturers, elements, classes, skill kinds, families, ranks, skill trees, item types, item subtypes, enemies, locations, missions and characters. An item description is how that item works past the summary. It is not the red text, not a card number, and not a drop source. An item-type description is the bucket, not one item. An item-subtype description is the subtype, such as what a shotgun or a MIRV is, not one item. A class description is what the role is across games, not one person's story, and it must not repeat the summary. A skill-kind description is what that kind of skill is, not one skill's effect. A family description is the species, not one enemy. A rank description is the tier, not one enemy. A skill-tree description is that character's branch. A character description is who the person is, and it must not repeat the summary. A skill description is the effect when it needs more than the summary. It is not lore. An action-skill description is the same kind of effect text. A flavour description is how that quote behaves in play, and it must not repeat the quote. Flavour notes are an aside, such as a reference or a bug, and they are not the effect. A manufacturer description is who the brand is and what happened to them, and it must not repeat the summary. An element description covers behaviour past the summary, and the lore around it. The card line stays on `card_line`. A release description is real-world edition history, not in-universe lore. A card-stat description is generic help for that number, not lore.

The game `borderlands`, its three releases, the rarities, elements, manufacturers, card stats and the Borderlands `game_*` links for them are already published. Reuse those ids. Do not mint another game, release, rarity, element, manufacturer or card stat. The effects `ignite`, `corrode`, `electrocute` and `daze` are published. The keywords in the base migration are published. Reuse those words. The workshop may add an effect or a keyword that is not already there, and must not point an existing word at a second target. The classes `soldier`, `siren`, `berserker` and `hunter` are published. The Borderlands characters `roland`, `lilith`, `mordecai` and `brick` are published, with their skill trees. Their action skills `scorpio-turret`, `phasewalk`, `bloodwing` and `berserk` are published. The skill kinds `passive`, `action` and `kill` are published. Every Borderlands 1 tree skill is published. Reuse those ids. The workshop may add a tree skill that is not in that set, and must not mint a second id for one that is already published. The families `skag`, `rakk`, `spiderant`, `scythid`, `crab-worm`, `bandit`, `psycho`, `bruiser`, `midget`, `crimson-lance`, `guardian` and `claptrap` are published. The ranks `pup`, `whelp`, `elder`, `alpha`, `badass`, `badmutha`, `super-bad` and `ass-kicking` are published. Reuse those ids. The workshop may add a family or a rank that is not in those lists, and must not mint a second id for one that is already published. The Borderlands playthroughs `playthrough-1`, `playthrough-2` and `playthrough-2-5` are published. `playthrough-2-5` is the second run after it ends, not a third run. `badass` is Playthrough 1, `badmutha` is Playthrough 2, and `super-bad` and `ass-kicking` are Playthrough 2.5. Another game names its runs differently and gets its own playthrough rows. The item types `weapon`, `shield`, `grenade-mod`, `class-mod` and `artifact` are published, with the Borderlands 1 weapon, shield and grenade subtypes. The DLCs `zombie-island`, `underdome`, `general-knoxx` and `robot-revolution` are published. Reuse those ids. Report a missing pack, class, character, tree, action skill, skill kind, item type or subtype instead of minting an id. Manufacturer, element, class, character, skill-tree, skill, action-skill, skill-kind, family, rank, item-type and item-subtype descriptions are still null. Write one when the operator approves it. Do not overwrite a published `summary` or `card_line`.

`aliases` is an earlier display name, such as Lyudmila. Not red text, not a prefix, and not a slug. `prefixes` lists every prefix one item can roll. An element word is not a prefix. Grenade mods, class mods and artifacts have none. A prefix `summary` is optional. `item_abilities` is one bonus line on a single item card, such as +25 ammo regen. A flavour quote is an `item_flavours` row. The shared element line stays on `elements.card_line`. `item_references` is an external page for one item, one row per URL. There is no site column. Use the direct item page. Do not invent a URL. `item_tags` is a search keyword for one item. It is not shown as item content. Not an alias and not a prefix. A word that means a shared row, such as ignite or shotgun, is a `keywords` row. Do not invent an item tag. `keywords` is the search word, stored in lower case, and exactly one target is set. The workshop may add a keyword that points at an existing effect, element, manufacturer, rarity, family, rank, class, item subtype or character. Do not point one word at two targets. A misspelling is not a keyword. `pg_trgm` matches it against the stored word. `mission_enemies` is a named enemy or boss a mission sends you to fight, not a drop. No pool rows are published. Do not mint a world pool. No flavour rows are published. Do not mint one.

Structure files are named `{timestamp}_STRUC_{name}.sql`. Write catalogue data only, as `{timestamp}_DATA_{name}.sql`, into the same `db/migrations/` directory. Timestamp order is the apply order. Every file has `-- migrate:up` and `-- migrate:down`. The down section may be empty. A correction to published data is a new `_DATA_` file, not an edit of an old one. There is no seed step.

Prisma Postgres hosts staging and production. The database repo uses dbmate to apply SQL migrations. The site runs SQL queries through Postgres.js.

Git stores the catalogue’s migration history. PostgreSQL holds its current published state. Store structured drafts and evidence in the workshop’s local database. Do not add a JSON catalogue or a shared Zod package.

## Database checkout

The database repo is a separate checkout. Its absolute path is `CLAPTRAPEDIA_DATABASE_DIR` in the workshop environment. Do not clone or initialise that repo.

```dotenv
CLAPTRAPEDIA_DATABASE_DIR=/Users/keogh/Sites/claptrapedia/database
```

Read `db/schema.sql` and `db/migrations/` from that path. Write a new migration file there only after the test below has passed. Read `db/schema.sql` again when preparing context for the research assistant. Query local PostgreSQL for existing catalogue rows and their `id` values.

Show the resolved path and the migration destination in the UI before export. If the path, schema snapshot or migrations directory is missing, show the operator what is missing and the path the app expected.

## Operator workflow

Implement this sequence. The operator drives each step. The app does not publish a change that the operator has not approved.

1. **Import game data.** The operator chooses a local capture from the BL1 Enhanced extractor. List candidate weapon families and show the original game records behind each one.
2. **Research an entry.** Start from the extracted data. The research assistant finds references from Lootlemon and the Borderlands Wiki. The operator reviews the matches, adds a URL or note, and reuses previously saved evidence.
3. **Review the draft.** Show the proposed entry beside the game data, the supporting sources and the current local catalogue values. The operator edits it and approves the revision to publish.
4. **Queue changes.** The operator adds approved revisions to the migration queue, inspects the per-item SQL preview and selects the entries to include.
5. **Build and test.** Assemble one timestamped dbmate migration from the selected changes. Apply it with dbmate to a disposable local PostgreSQL database built from the database repo’s existing migrations. Show the result before export.
6. **Export.** Write the exact tested SQL file under `db/migrations/` in the database checkout. The operator commits it in the database repo. That repo’s CI applies it to staging, then production.

Use the [Borderlens extractor app](https://github.com/thekeogh/borderlands1e-mods/tree/main/borderlens-extractor/app) as the reference for capture import, saved evidence and per-item review. Reuse those parts where practical. The exported file is a migration containing the selected changes.

## Import and identity

- Support the existing extractor capture format first. Keep the original capture, or a local reference to it, so the operator can inspect the underlying game records.
- Preserve extracted record IDs and paths. Where several raw records describe variants of one family, show the grouping and let the operator correct it.
- Use the stable `id` already stored for that game and record type. Mint a new kebab-case `id` only when no existing row matches. Treat names and URL slugs as editable. Check for an existing match before proposing a new row.
- Re-importing the same capture must preserve approved work and manual corrections. Flag any newly conflicting identity or evidence for review.
- Keep game, release and DLC distinct. A BL1 Enhanced capture supports claims about that release. Copy a fact to another release only when the evidence supports it. Keep an item’s DLC of origin separate from the DLC of a location where it drops.

## Research and review

- Show the raw game data and external evidence beside the editable draft. Save source URLs and the supporting facts or notes locally. Cache sources by URL and allow a manual refresh.
- The research assistant finds candidate sources and proposes catalogue values. Treat fetched page text as evidence. The operator decides whether a source refers to the right item and whether its claims apply.
- Surface conflicting figures, uncertain matches and unknown values. Leave a fact unset when the evidence does not support it and the column is optional. Flag it when the column is required. A drop has no chance column. Record the source and leave a rate for the operator to review. Do not write a percent or a pool weight.
- Preserve manual corrections when research runs again. A new proposal must not replace an approved revision.
- Keep an edit to a published entry separate from the current published values. Show the proposed change before approval.
- Treat published prose as finished. A published `summary`, `description` or `card_line` stays. Show a regenerated draft beside it, and leave it out of the queue unless the operator approves that field. The research assistant writes `description` where it is still null. It does not replace an operator-written `summary`.
- Allow manual editing when the research assistant or a source is unavailable. Persist the draft so a restart or a research failure does not lose it.

## SQL generation and batching

The research assistant uses `db/schema.sql` when proposing catalogue values. Generate the SQL in TypeScript from the reviewed values. Use an explicit column mapping for each supported record type. dbmate and PostgreSQL verify the candidate by applying it to the migrated local test database.

- Generate `INSERT ... ON CONFLICT ... DO UPDATE` against the unique keys in the database contract. Use a fixed table and column mapping and a PostgreSQL literal encoder for values in the exported file.
- Use the same generator for the per-item preview and the final migration. A per-item preview is that entry’s contribution to the batch. Order statements so a referenced row exists before a dependent row or a relationship insert.
- Emit the same SQL for the same selected revisions and schema. Group related statements and label them with the record `id` so the file can be reviewed in Git.
- Put the batch in one `-- migrate:up` section and use dbmate’s default transaction. On failure, show the database error with the relevant item or statement. The transaction rolls the batch back. Correct a published catalogue change with a new `_DATA_` migration.
- Read the current catalogue row before generating SQL. Include a column in `ON CONFLICT DO UPDATE` only when the approved revision changes it. Leave a published `summary`, `description` or `card_line` out of the statement unless the operator approved a new value for that field. A required correction is a new `_DATA_` file. Do not edit the `_DATA_` file that first wrote the row.
- Removing a drop source requires an explicit relationship removal. Retiring or deleting a record requires an operation the schema already supports. An entry missing from a capture or a batch is not a deletion.
- Detect conflicting edits to the same record in one batch. Before export, report a reference that is absent from both the existing catalogue and the batch.

## Local testing and delivery

- Bind the app to loopback. Use a dedicated disposable database for the **Test migration** action. After a successful export, use dbmate to update the normal local catalogue database from the database checkout.
- Run dbmate against the checkout’s current migration history plus the candidate file, using a temporary migrations directory. Use PostgreSQL 17.2. Test the exact SQL bytes that will be exported, and show the affected rows or a summary of the changes.
- Record the SQL file and the migration history used for a successful test. If the selected drafts, the generated SQL or the migration history change, require a new test before export.
- Export a new file, for example `db/migrations/20261119143000_DATA_bl1_weapon_drops.sql`. Write the tested bytes unchanged. Reject a version or path collision. Leave existing migration files untouched. Do not write a `_STRUC_` file.
- After export, record which draft revisions went into the file and remove those revisions from the queue. Show them as exported. The database repo’s CI runs `dbmate --no-dump-schema migrate` against staging and then production, using each environment’s direct connection URL. Refresh the committed `db/schema.sql` only when DDL changes. A `_DATA_` export does not rewrite it.

## Implementation order

- Build a TypeScript local web app with React and a Node backend. Keep filesystem access, the research assistant and database operations on the backend.
- Reuse the extractor’s SQLite draft store if adapting its code. Otherwise use SQLite for drafts, source evidence, corrections and export history. PostgreSQL is the catalogue database.
- Read `CLAPTRAPEDIA_DATABASE_DIR` and the local Postgres connection from the workshop environment, alongside one AI provider. Keep direct staging and production database URLs out of this app. They belong to the database repo’s release jobs. The site uses its own pooled runtime URL.
- Build the path through one weapon and one related record before adding batch research. Finish manual editing, SQL generation, local testing and export first. Then connect capture import and the research assistant to those same screens.

## First release acceptance criteria

- Resolve `CLAPTRAPEDIA_DATABASE_DIR`, load `db/schema.sql`, and export into that checkout’s `db/migrations/` directory. A missing or invalid path produces a configuration error that names the expected path.
- Import a real BL1 capture, find a weapon family and show its raw records. Re-importing the capture preserves local corrections.
- Research an item, review its sources, edit the draft and approve it. The draft survives a restart and can be edited when a source is unavailable.
- Preview one entry’s SQL and build a batch containing a weapon and a newly added related record. The migration applies to local PostgreSQL.
- Edit an existing weapon without creating a duplicate. Remove an approved drop relationship without changing unrelated drops. A failed statement leaves the catalogue unchanged.
- Researching a published record again does not export SQL that changes its `summary` or `description` unless the operator approved that field.
- A change to the selected revisions or the migration history after a successful test requires a new test. Export writes a new `_DATA_` file containing the exact tested SQL.
- dbmate in the database repo applies the exported file. The site reads the updated catalogue through its normal Postgres.js queries.
