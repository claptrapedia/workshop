# Claptrapedia workshop specification

Build Claptrapedia Workshop, a local app for maintaining the [Claptrapedia](https://claptrapedia.com) Borderlands catalogue. It turns game extracts and reference material into reviewed catalogue changes, then exports a PostgreSQL migration for the public site.

The first release covers Borderlands 1. The workshop is based on one uploaded Borderlands 1 Enhanced extract, then uses LootLemon and the Borderlands Wiki to fill what that extract does not. Prove the path on one weapon and the enemies, locations and missions that source it, then use the same screens for the rest of the extract. A later game is another extract and another `game_id`. Do not build that game now. Keep `game_id` on every record and keep the review loop free of Borderlands 1-only assumptions where that is a small choice. Do not add a plugin system or a second game's slots to make the future easy.

## Build in chunks

Build the app in the six chunks below, in order. Finish a chunk, write tests for the behaviour that chunk claims, run them with `pnpm test`, then stop and let the operator run the app. Do not start the next chunk in the same stretch of work. A chunk is one session of testing, not a single button and not the whole app. The tests cover the store and the rules. They do not cover the look of the screens. If the operator changes a rule, update this specification and the tests together.

1. **Extract library.** The upload splash, the unzipped extract, and the working set rendered with the raw records behind a candidate. The list is grouped and searchable, with delete, restore, duplicate suggestions, a type correction, and the card image. Snapshot export and import, including a snapshot that fails its check. **Reset app** returns to the splash. No agent calls, no web capture, and no SQL.
2. **Agents.** The header switch, and one action that sends a short prompt to the selected CLI and shows the reply and the model that ran. Claude Code and Codex both have to succeed. No catalogue prose yet.
3. **One source.** The wiki parse proof and the LootLemon rendered proof. **Open**, **Fetch**, and the capture modal on those proofs. The progress bar covers that fetch.
4. **One weapon draft.** **Find pages** for one weapon, and nothing else: the URLs are stored and a rejected URL stays rejected. Then capture those pages. A general page can be shared onto one scope with **Share with**, and the draft for that weapon includes the matching shared capture. The selected agent writes the draft. The review screen shows the draft beside the raw records. The operator can edit and approve it. No migration file yet.
5. **One migration.** SQL for that approved weapon, applied on `127.0.0.1:5433`, then written to the database checkout only if the apply succeeds. **Apply locally** is on screen and does nothing until the operator clicks it. Copy that weapon's card image when the file is written and the image exists.
6. **Runs.** **Check for updates** on the sources that weapon stored, including a shared URL once. Then **Find pages** and a full run, each at one item, one subtype, one type, and everything, with the progress bar and **Refetch** off by default. A shared URL is captured once in the run, not once per item. Pause, resume, cancel, browse during the run, and **Needs attention**, with the full error text.

## Repositories and ownership

| Repository | Owns |

| [`claptrapedia/extractions`](https://github.com/claptrapedia/extractions) | Raw game extractions used as workshop inputs |
| [`claptrapedia/workshop`](https://github.com/claptrapedia/workshop) | Import, research, review, local drafts, SQL generation and testing |

| [`claptrapedia/site`](https://github.com/claptrapedia/site) | Next.js site, SQL queries via Postgres.js (`postgres`) and website deployment |

Treat the database repo’s `db/migrations/` as the source of truth for schema and catalogue changes. Its generated `db/schema.sql` is the current schema, including the `COMMENT` text on tables and columns. Read those comments before generating SQL. Take table names, column names, data types, constraints and conflict keys from that snapshot and from the migrated local database. If the schema cannot represent a catalogue fact, stop and report that fact for review. Do not invent a table inside a data migration. A structural change belongs in a `_STRUC_` file. This workshop does not write those files.

### Database contract

Target PostgreSQL 17.2. Catalogue objects live in the `catalogue` schema. `public` holds dbmate’s `schema_migrations` table and the `pg_trgm` extension. Qualify every catalogue table, for example `catalogue.enemies`. The database does not set `search_path`. `pg_trgm` stays in `public` so `similarity` and the `%` operator resolve on the default path.

The migrated tables are `games`, `releases`, `dlcs`, `playthroughs`, `rarities`, `game_rarities`, `elements`, `game_elements`, `effects`, `manufacturers`, `game_manufacturers`, `classes`, `skill_kinds`, `families`, `ranks`, `rank_playthroughs`, `characters`, `skill_trees`, `action_skills`, `skills`, `enemies`, `locations`, `missions`, `mission_enemies`, `card_stats`, `game_card_stats`, `item_type_card_stats`, `item_types`, `item_subtypes`, `part_slots`, `parts`, `part_modifiers`, `items`, `item_images`, `item_part_slots`, `item_parts`, `item_manufacturers`, `item_rarities`, `item_elements`, `item_stat_ranges`, `item_rolls`, `item_skills`, `item_flavours`, `item_abilities`, `aliases`, `prefixes`, `item_references`, `item_tags`, `keywords`, `pools` and `drops`. Weapon, shield and grenade extension tables do not exist. `items` has `id`, `game_id`, `dlc_id`, `slug`, `name`, `item_type_id`, `subtype_id`, `character_id`, `plain`, `projectile_min`, `projectile_max`, `summary` and `description`. `slug` and `name` are unique within the game. `projectile_min` and `projectile_max` are the xN beside damage on a weapon. Both are null when the card shows no xN, and on every item that is not a weapon. A fixed x6 stores 6 and 6. Damage, accuracy, fire rate and magazine are not columns on `items`. The part spread is `item_stat_ranges`. The one shown card is `item_rolls`. Do not invent another stat column, and do not invent a drop chance column. Do not emit SQL for a table or column that is absent from `db/schema.sql`.

`id` is a stable lowercase kebab-case key the workshop chooses, such as `bone-head`. It is not a generated number or UUID. The published Borderlands 1 game id is `borderlands`. `slug` is the public URL and may change. Names and slugs are editable. Use the primary key as the conflict target. That is `(id)` on `games`, `rarities`, `elements`, `effects`, `manufacturers`, `classes`, `skill_kinds`, `families`, `ranks`, `item_types` and `card_stats`, and `keyword` on `keywords`, and `(id, game_id)` on `releases`, `dlcs`, `playthroughs`, `characters`, `enemies`, `locations`, `missions`, `items` and `pools`. `item_images` is `(item_id, game_id, kind)`. `skill_trees` is `(id, character_id, game_id)`. `rank_playthroughs` is `(rank_id, game_id)`. Link tables use the whole primary key: `(game_id, rarity_id)` on `game_rarities`, and the same shape for `game_elements`, `game_manufacturers` and `game_card_stats`. `item_type_card_stats` is `(item_type_id, card_stat_id)`. `mission_enemies` is `(mission_id, game_id, enemy_id)`. `item_manufacturers` is `(item_id, game_id, manufacturer_id)`. `item_rarities` is `(item_id, game_id, rarity_id)`. `item_elements` is `(item_id, game_id, element_id)`. `item_stat_ranges` is `(item_id, game_id, card_stat_id)`. `item_rolls` is `(item_id, game_id)`. `item_skills` is `(item_id, game_id, skill_id)`. `item_flavours` and `item_abilities` are `(item_id, game_id, position)`. `aliases` and `prefixes` are `(item_id, game_id, name)`. `item_references` is `(item_id, game_id, url)`. `item_tags` is `(item_id, game_id, keyword)`. `skills` and `action_skills` are `(id, character_id, game_id)`. `item_subtypes` is `(id, item_type_id)`. `part_slots` is `(id, item_type_id)`. `parts` is `(id, item_type_id, slot_id)`. `part_modifiers` is `(part_id, item_type_id, slot_id, position)`. `item_part_slots` is `(item_id, game_id, slot_id)`. `item_parts` is `(item_id, game_id, part_id, slot_id)`. `drops` has no `id`. Its conflict target is `(item_id, game_id, enemy_id, location_id, mission_id, pool_id)`, and nulls compare equal. A DLC reference is the pair `(dlc_id, game_id)`. Null `dlc_id` means the base game.

Rarities, elements, manufacturers, classes, skill kinds, families, ranks, item types, item subtypes and card stats are shared across games. A `game_*` row says that value exists in that game. Pools are per game. A world pool is a `drops` row with `pool_id` set and the enemy, location and mission null. A dedicated source is a separate `drops` row. Do not add an item-pools table. An alias is an earlier item name, not a second item. A prefix belongs to one item. The same word on another item is another row. Read the `COMMENT` text for the rest of these rules.

Keep `games`, `releases` and `dlcs` distinct. Borderlands 1 is a game. The original edition, GOTY and GOTY Enhanced are releases of that game. A BL1 Enhanced capture supports claims about that release. A DLC is the pack that introduced an enemy, not the place where it appears. `family_id` points at the shared species, such as `skag`. `rank_id` points at the shared tier, such as `badass`, and is null when the enemy is not a tier. `position` is display order. `kind` on an enemy is `named`, `boss` or `mob`. A named enemy is not always a boss. A character is the playable person in one game, such as Lilith. `class_id` points at the shared class, such as `siren`. Another game's Siren is another character row with the same `class_id`. A class, a skill kind, a family, a rank, an item type or an item subtype is in a game when a row there uses it. Do not add a `game_classes`, `game_skill_kinds`, `game_families`, `game_ranks`, `game_item_types` or `game_item_subtypes` table. A rank has no `game_id`. The same word, such as Badass, is one row in every game, and its summary must not name a playthrough. Which run uses that name is `rank_playthroughs`. A rank such as Whelp has no playthrough row. A character is not an enemy. A skill belongs to one character, such as Roland's Impact. `id` is the skill within that character, such as `impact`. `tree_id` points at that character's branch, such as `infantry`, and it is required. `kind_id` points at the shared skill kind, such as `passive` or `kill`. An action skill is a row in `action_skills`, not in `skills`. `cooldown` and `duration` are the base seconds before other skills change them. `duration` is null when the skill is not a timed mode. The site prints `name` from the kind, the tree, the family, the rank, the item type and the item subtype. That name is the exact label. A different wording of the same thing is not a new row. `tier` 0 is the first row. `points` is the maximum. The same skill name on another character is another row. Do not hang a skill on the class. An item type is the inventory bucket, such as `weapon` or `grenade-mod`. An item subtype is the second label inside that bucket, such as `shotgun` or `mirv`, and its primary key includes `item_type_id`. Class mods and artifacts have no subtype. A character is not a subtype. `items.item_type_id` is required. `items.subtype_id` is required for a weapon, a shield and a grenade mod, and null for a class mod or an artifact. The foreign key is `(subtype_id, item_type_id)`. `items.character_id` is required for a class mod or an artifact and null for the other buckets. It is the person, such as `roland`, not the shared class. `items.plain` is true when a spawn can have no element, including a gun that never has one. `item_elements` lists every element a spawn can have. Do not insert a `none` element. `multiplier_min` and `multiplier_max` on that row are the x1 to x4 tech rating for that element. A fixed x4 stores 4 and 4. A roll from x1 to x3 stores 1 and 3. Leave both null when that element has no tech rating, such as a shield. `projectile_min` and `projectile_max` are how many projectiles one shot fires. They are not the tech rating and not the ammunition used per shot. `item_type_card_stats` says which buckets can show a card stat. `damage` is on a weapon, a grenade mod and a shield. `capacity`, `recharge-rate` and `recharge-delay` are on a shield. `accuracy`, `fire-rate`, `magazine`, `projectile-count` and `element-multiplier` are on a weapon. A class mod and an artifact have none. Their numbers are skill points or bonus lines. `item_stat_ranges` is the part spread for `accuracy`, `fire-rate`, `magazine` and `recharge-delay`. One row per stat. `value_min` and `value_max` are the low and high ends. `item_type_id` is the item's bucket, and that pair must already be on `item_type_card_stats`. Do not insert `damage`, `capacity` or `recharge-rate` there. The level sets those. `item_rolls` is the one card the site shows for that item, at `level`. A weapon stores `damage`, `accuracy`, `fire_rate` and `magazine`. A shield stores `capacity`, `recharge_rate` and `recharge_delay`, and `damage` when the shield itself deals damage, such as a nova. A grenade mod stores `damage`. The other numbers on that row stay null. A class mod and an artifact have no roll. `element_id` is the element on that card, null when it has none, and it must already be on `item_elements`. `projectiles` is the yellow xN on a weapon card. Leave it null when `projectile_min` and `projectile_max` are equal. `multiplier` is the tech rating on a weapon card. Leave it null when the card has no element, and when `multiplier_min` and `multiplier_max` on that element are equal. Set either one only when the card picked a value inside the spread. One roll per item. No roll rows are published. `part_slots` is a slot on one bucket, such as barrel on a weapon or left on a shield. The same id under another bucket is another row. Grenade mods and artifacts have no slots. Do not invent one. `parts` is one mechanical part in a slot, shared by every item of that bucket that can roll it. A renamed unique part is its own row. `subtype_id` is set when the part only fits one weapon type. `manufacturer_id` is set when the part belongs to one brand, such as a Maliwan material. That is not a brand printed on the item card. `part_modifiers` is one change that part makes, written as the player reads it. Do not copy that line onto `item_abilities` or a prefix. `item_part_slots` is how many of that slot an item can carry. An accessory is often 0 to 1. A body is 1 to 1. `item_parts` is a part that item can spawn with. `required` is true when the item always has that part. A unique that cannot roll a part has no link to it. No part rows are published. `item_images` is one picture of an item. `kind` `card` is the render in `Workshop/src/data/img`. `path` is relative to that folder and includes the game and the bucket, for example `borderlands/weapons/hellfire.png`. The same stem exists in two buckets, so the path is not the slug. No image rows are published. Add one when that file exists. A second role is another row of `image_kind`, not a new column. `item_manufacturers` is one brand on a gun, shield or grenade, and each brand printed on a class mod. A part's brand is not a row there. `item_rarities` is every tier the item can spawn as. A unique is one row. Those three joins must use a rarity, element or manufacturer already linked to that game. `item_skills` is the bonus points a class mod adds to one of that character's tree skills. `points` may sit above the skill's own maximum. It is not an action skill, and a card line that is not a skill point stays on `item_abilities`. `item_flavours` is a flavour line and what that line does. `kind` is `red` or `white`. `quote` is the words on the card. `summary` is the one-line effect. `description` is the longer effect. `notes` is an aside that is not the effect. `self` is true when the effect applies to the wielder. An item has at most one red row. A white row is other flavour text, such as a joke on the card. Do not store a flavour quote on `item_abilities`.

Generated values must satisfy the domains in `db/schema.sql`. `catalogue.slug` is lowercase kebab-case. `catalogue.summary` is one line. `catalogue.non_empty` rejects blank text. `catalogue.url` is an absolute http or https address with no spaces. `catalogue.image_kind` is `card`. A new picture role is a new value on that domain. Leave an unknown optional value null. Do not write an empty string.

`description` is the long body and may run to more than one paragraph. Use it for lore on manufacturers, elements, classes, skill kinds, families, ranks, skill trees, item types, item subtypes, enemies, locations, missions and characters. An item description is how that item works past the summary. It is not the red text, not a card number, and not a drop source. An item-type description is the bucket, not one item. An item-subtype description is the subtype, such as what a shotgun or a MIRV is, not one item. A class description is what the role is across games, not one person's story, and it must not repeat the summary. A skill-kind description is what that kind of skill is, not one skill's effect. A family description is the species, not one enemy. A rank description is the tier, not one enemy. A skill-tree description is that character's branch. A character description is who the person is, and it must not repeat the summary. A skill description is the effect when it needs more than the summary. It is not lore. An action-skill description is the same kind of effect text. A flavour description is how that quote behaves in play, and it must not repeat the quote. Flavour notes are an aside, such as a reference or a bug, and they are not the effect. A manufacturer description is who the brand is and what happened to them, and it must not repeat the summary. An element description covers behaviour past the summary, and the lore around it. The card line stays on `card_line`. A release description is real-world edition history, not in-universe lore. A card-stat description is generic help a player reads under that number, not lore, and not a workshop rule.

The game `borderlands`, its three releases, the rarities, elements, manufacturers, card stats and the Borderlands `game_*` links for them are already published. Reuse those ids. The effects `ignite`, `corrode`, `electrocute` and `daze` are published. The keywords in the base migration are published. Reuse those words. The workshop may add an effect or a keyword that is not already there, and must not point an existing word at a second target. The classes `soldier`, `siren`, `berserker` and `hunter` are published. The Borderlands characters `roland`, `lilith`, `mordecai` and `brick` are published, with their skill trees. Their action skills `scorpio-turret`, `phasewalk`, `bloodwing` and `berserk` are published. The skill kinds `passive`, `action` and `kill` are published. Every Borderlands 1 tree skill is published. Reuse those ids. The workshop may add a tree skill that is not in that set, and must not mint a second id for one that is already published. The families `skag`, `rakk`, `spiderant`, `scythid`, `crab-worm`, `trash-feeder`, `drifter`, `craw-worm`, `bandit`, `psycho`, `bruiser`, `midget`, `crimson-lance`, `guardian`, `claptrap`, `zombie`, `wereskag`, `skelerakk`, `tankenstein` and `loot-goon` are published. `craw-worm` is the craw, including the maggot. `zombie` is the ordinary undead person. `drifter` is the long-legged burrower, not a zombie. A corpse eater is a `trash-feeder`. The ranks `pup`, `whelp`, `elder`, `alpha`, `badass`, `badmutha`, `super-bad` and `ass-kicking` are published. Reuse those ids. The workshop may add a family or a rank that is not in those lists, and must not mint a second id for one that is already published. The Borderlands playthroughs `playthrough-1`, `playthrough-2` and `playthrough-2-5` are published. `playthrough-2-5` is the second run after it ends, not a third run. `badass` is Playthrough 1, `badmutha` is Playthrough 2, and `super-bad` and `ass-kicking` are Playthrough 2.5. Another game names its runs differently and gets its own playthrough rows. The item types `weapon`, `shield`, `grenade-mod`, `class-mod` and `artifact` are published, with the Borderlands 1 weapon, shield and grenade subtypes. The shield subtype `health-boost` is the max-health effect. `healing` is health returned over time. Do not mint a second id for either. The DLCs `zombie-island`, `underdome`, `general-knoxx` and `robot-revolution` are published. Reuse those ids. Manufacturer, element, class, character, skill-tree, skill, action-skill, skill-kind, family, rank, item-type and item-subtype descriptions are still null. Write one when the operator approves it.

Published rows are the current catalogue, not a closed list. The workshop may add a missing record, and it may delete one that should not be there. Reuse the published id when it is the same thing. A second id for a new wording of that thing is a duplicate. An update ships only when the facts changed: a wrong creature, a wrong number, or a behaviour the sentence does not mention. Rewording the same facts is not a change. Generated prose comes out differently on every run, so a regenerated `summary`, `description` or `card_line` stays out of the queue.

`aliases` is an earlier display name, such as Lyudmila. Not red text, not a prefix, and not a slug. `prefixes` lists every prefix one item can roll. An element word is not a prefix. Grenade mods, class mods and artifacts have none. A prefix `summary` is optional. `item_abilities` is one bonus line on a single item card, such as +25 ammo regen. A flavour quote is an `item_flavours` row. The shared element line stays on `elements.card_line`. `item_references` is an external page for one item, one row per URL. There is no site column. Use the direct item page. Do not invent a URL. `item_tags` is a search keyword for one item. It is not shown as item content. Not an alias and not a prefix. A word that means a shared row, such as ignite or shotgun, is a `keywords` row. Do not invent an item tag. `keywords` is the search word, stored in lower case, and exactly one target is set. The workshop may add a keyword that points at an existing effect, element, manufacturer, rarity, family, rank, class, item subtype or character. Do not point one word at two targets. A misspelling is not a keyword. `pg_trgm` matches it against the stored word. `mission_enemies` is a named enemy or boss a mission sends you to fight, not a drop. The Borderlands world pools `repeater-pistol`, `revolver`, `smg`, `combat-rifle`, `shotgun`, `sniper-rifle`, `rocket-launcher`, `eridian-weapon`, `shield` and `grenade-mod` are published. Reuse those ids for those tables. Add a pool only when it is a different shared table. A class mod or an artifact has no pool. No flavour rows are published. Add one only when the card shows that quote.

Structure files are named `{timestamp}_STRUC_{name}.sql`. Write catalogue data only, as `{timestamp}_DATA_{name}.sql`, into the same `db/migrations/` directory. Timestamp order is the apply order. Every file has `-- migrate:up` and `-- migrate:down`. The down section may be empty. A correction to published data is a new `_DATA_` file, not an edit of an old one. There is no seed step.

Prisma Postgres hosts staging and production. The database repo uses dbmate to apply SQL migrations. The site runs SQL queries through Postgres.js.

Git stores the catalogue’s migration history. PostgreSQL holds its current published state. Store structured drafts and evidence in the workshop’s local database. Do not add a JSON catalogue or a shared Zod package.

## Agents

Research, matching, and every sentence of catalogue prose are done by the selected agent. The app does not call the Anthropic or OpenAI APIs. It shells out to the CLIs already installed and logged in on this machine, so the operator's Claude and ChatGPT subscriptions are what run.

- Claude Code is `claude -p` with `--output-format json`. This is the default agent.
- Codex is `codex exec`. Use it when the operator selects it. A failed or hung call tries the other CLI once for that step. If both fail, the item is marked and the run continues. The run stops if the selected CLI is missing.
- Pass the model through the CLI's own `--model` flag. Claude Code's model is Sonnet 5.5 at medium effort. Codex's model is GPT Sol 6.2 at medium effort. If a CLI rejects that name, report the error and the models that CLI lists, then use the medium Sonnet or medium GPT model it does offer. Record which model ran. Do not stop the workshop to ask for a slug.
- Prose, once the facts are already decided, may use a lower effort on that same agent. Catalogue judgement stays at medium.
- The prompt contains the facts, the column rules, and the current published sentence. It asks the agent to write the sentence. The app stores the sentence the agent returns. It may trim whitespace. It does not rewrite, wrap, or assemble that sentence in code.
- A template, a concatenated string, or a fill-in function is not prose. Do not ship one.

## Shared sources

A shared source is one page that applies to many items. It is captured once and reused. The fire page is the case: it describes the element, not the Hellfire, so it is not stored again on every fire gun.

The operator adds the URL, or uses **Share with** on a URL already saved for one item. **Share with** moves that URL onto one scope and takes it off the item. The capture stays. **Find pages** does not go looking for shared pages. If it returns a URL that is already shared for a scope this item matches, the URL stays shared and is not copied onto the item.

A scope is one of the game, an item type, a subtype, a character, an element, or a manufacturer. One URL belongs to one scope. The same **Open**, **Fetch**, capture modal, rejection, and change signal apply. There is no per-item switch for include or exclude. Removing the shared URL is how it stops applying. A shared capture does not make an item ready. The item still needs its own captured page. When a draft is written, the agent also receives the shared captures that match. The page text is still not copied into a prose field.

## Runs

A run walks the working set one item at a time. The operator picks the scope and the job:

- **Everything** sits at the top of the app: one large progress bar, **Find pages**, and the full run. It walks every candidate in the working set.
- **Type** walks one bucket, such as every weapon or every shield.
- **Subtype** walks one subtype, such as every SMG or every MIRV. A candidate whose subtype is not known yet is in the type run only.
- **Item** is a button on that item, such as the Hellfire. The run is that item alone.

**Find pages** is its own job, on every scope, including one item and everything. It searches LootLemon and the wiki, stores the direct URLs, and stops. It does not capture a page, does not write prose, and does not write a draft. A URL the operator has rejected is not stored again. A URL already shared for a matching scope is left shared. The full run is the other job. It finds any missing pages, captures each shared URL once, then captures, drafts, and continues through the workflow below.

The same bar is used for every scope and both jobs, including one item. It stays up for the whole run. It shows how many items are done, how many were skipped, and how many remain, and it names the current item and the current step. Any step that takes time reports on that bar: finding pages, fetching a source, writing prose, testing a migration, exporting. A step that is waiting on the agent says so. The bar does not paste page text. The capture modal still holds the stored text.

Opening another item, or a capture modal, while a run is going does not pause it and does not cancel it. Closing the browser tab does not stop it. The run keeps going on the machine.

**Pause** finishes the call or capture already in flight, then stops. The queue and the finished items stay. **Resume** continues that same scope and job, including after the app is restarted. A run that was not paused and not cancelled also continues after a restart, from the next unfinished item. **Cancel** clears the queue. Finished items, captures, and drafts stay. A paused run stays paused across a restart until **Resume**.

A run is meant to be left. It continues through a skip, a page whose check cannot be passed, and a model name the CLI rejected. A failed or hung agent call tries the other CLI once for that step. If both fail, the full output is stored on that item, the item goes to **Needs attention**, and the run takes the next item. The run stops only on a hard error: the database is down, the selected CLI is missing, or a write to disk failed. The bar then shows which item stopped and the full error. Items already finished stay finished. A first pass still waits for approval, so a run saves the draft and moves on. It does not approve the draft and it does not export that first migration. A later capture whose facts changed still writes its tested `_DATA_` file, then the run takes the next item.

**Refetch** is a toggle on the run, off by default. While it is off, a source whose change signal is unchanged is skipped: the run says so, and it does not download, call the agent, or replace prose. While it is on, the run captures that source again as if it were new. A capture whose facts are unchanged still leaves the published sentence where it is, and it does not write a migration. The extension replacing a capture is the operator's selection, and it stores that selection either way.

## SQL generation and batching

The selected agent uses `db/schema.sql` when proposing catalogue values. Generate the SQL in TypeScript from the reviewed values. Use an explicit column mapping for each supported record type. dbmate and PostgreSQL verify the candidate by applying the exact SQL to the disposable database on `127.0.0.1:5433`. Export is refused until that apply succeeds. The catalogue database on port 5432 is not part of the test.

- Generate `INSERT ... ON CONFLICT ... DO UPDATE` against the unique keys in the database contract. Use a fixed table and column mapping and a PostgreSQL literal encoder for values in the exported file.
- Use the same generator for the per-item preview and the final migration. A per-item preview is that entry’s contribution to the batch. Order statements so a referenced row exists before a dependent row or a relationship insert.
- Emit the same SQL for the same selected revisions and schema. Group related statements and label them with the record `id` so the file can be reviewed in Git.
- Put the batch in one `-- migrate:up` section and use dbmate’s default transaction. On failure, show the database error with the relevant item or statement. The transaction rolls the batch back. Correct a published catalogue change with a new `_DATA_` migration.
- Read the current catalogue row before generating SQL. Include a column in `ON CONFLICT DO UPDATE` only when the approved revision changes it. Leave a published `summary`, `description` or `card_line` out of the statement unless the new value records a fact the published sentence does not. A rewording is not that change. A required correction is a new `_DATA_` file. Do not edit the `_DATA_` file that first wrote the row.
- Removing a drop source requires an explicit relationship removal. Retiring or deleting a record requires an operation the schema already supports. An entry missing from a capture or a batch is not a deletion.
- Detect conflicting edits to the same record in one batch. Before export, report a reference that is absent from both the existing catalogue and the batch.
